# ADR-0007: Playwright MCP Server as the Testing Pipeline Driver

**Status:** Accepted  
**Date:** 2026-04-11  
**Deciders:** Agent Studio Architecture Team

## Context

The testing pipeline is a critical quality gate in Agent Studio's delivery loop. After the Coder role produces a change, the Tester role must generate test specifications, execute them, interpret results, and — on failure — find a fix before passing control to the Reviewer. The naive approach to this loop has two well-known failure modes: running all tests in the repository (expensive in time and cost, especially in large repos), and retrying failures by immediately re-dispatching to the Coder without checking whether the failure pattern has been seen before (missing the opportunity to reuse a known solution and burning tokens on a problem already solved).

The test execution environment must be sandboxed. Browser automation (E2E and UI component tests) requires a real browser, which is a heavy and potentially dangerous runtime if run directly on the orchestrator host. Code produced by agents is untrusted; if that code crashes a test runner or attempts to write outside the workspace, the sandbox should absorb the impact without affecting the orchestrator process or other tenants' workloads.

Three options for the test execution layer were evaluated: (1) shell-exec a test command directly from the Coder's Claude Code worker, (2) build a bespoke test orchestration service, and (3) use the Playwright MCP server (`@playwright/mcp`) running inside a Docker sandbox. Option 1 gives no isolation, mixes test execution into the coding worker's tool budget, and provides no structured output for the orchestrator to reason about. Option 2 duplicates infrastructure that already exists in the Playwright project. Option 3 provides browser automation, structured JSON/HTML test reports, screenshot capture, and a clean MCP tool interface — all within the same allowlist and observability infrastructure used by every other capability.

Determining which tests to run is equally important. Without structural code knowledge, the Tester would have to run the full suite or guess based on filename conventions. The code-review-graph MCP server (ADR-0006) provides `graph.tests_for` and `graph.impact_radius` — exact, graph-derived sets of tests relevant to the changed code. Using these to scope the test run avoids both under-testing (missing tests for indirectly affected code) and over-testing (running the full suite when only a small subsystem changed).

## Decision

The Tester agent role drives the testing pipeline through the Playwright MCP server, which runs inside a Docker sandbox (one container per task, resource-limited, network-egress restricted). The test surface is determined before any test is executed: the Tester first calls `graph.tests_for` and `graph.impact_radius` on the set of files changed by the Coder (obtained from the most recent `graph.detect_changes` result) to get the graph-derived set of tests to run. Spec files that do not yet exist are generated by dispatching a Claude Code worker session with the appropriate goal and workspace context.

On test failure, before dispatching a fix to the Coder's Claude Code worker, the Tester calls `memory.search` (Ruflo) and `knowledge.search` (internal Knowledge Retrieval MCP, ADR-0008) with the failure message as the query. If a known solution is returned, it is injected into the Coder dispatch envelope as `memoryContext` and `knowledgeContext` — the fix starts with a pre-loaded answer rather than discovering it from scratch. After the Coder applies a fix (committed via Git MCP), the orchestrator calls `graph.update` to refresh the code graph, and the Tester re-runs the scoped test set. The loop exits when pass-rate and coverage thresholds are met, or when the maximum iteration count is reached, at which point the task transitions to a `blocked` state awaiting human review.

## Consequences

### Positive
- The Docker sandbox fully isolates browser automation from the orchestrator host; a runaway browser process, a crashing test runner, or a test that attempts to write outside the workspace cannot affect other tenants or the orchestrator itself.
- Graph-derived test scoping via `graph.tests_for` + `graph.impact_radius` eliminates wasted test runs and ensures that indirectly affected code paths are included in the test surface.
- Memory and knowledge retrieval before dispatching a fix means known failure patterns are recognized and reused instead of re-discovered, reducing token cost and iteration count on recurring failure types.
- Playwright's structured JSON/HTML reports and screenshots provide rich, inspectable failure evidence that is surfaced in the Web UI and can be attached to the Delivery Bundle.
- The Playwright MCP server is the only role allowed to call `playwright.*` tools (enforced by the per-role allowlist, ADR-0010), preventing other roles from triggering browser automation inadvertently.

### Negative / Trade-offs
- Docker container spin-up time adds latency to the first test execution per task. For short unit tests that do not require a browser, this overhead is disproportionate; the architecture accepts this trade-off in favor of uniform sandboxing across all test types.
- The Tester role is blocked if the Playwright MCP server is unreachable (container startup failure, registry misconfiguration). This is a hard dependency for the test loop; the fallback is to emit a HITL event requesting human confirmation of whether to proceed without automated testing.
- Graph-derived test scoping requires that the code-review-graph be up to date; a stale graph (e.g. after a very large coder commit) could produce an inaccurate test surface. The `graph.update` call after every commit mitigates this but adds latency to each loop iteration.
- Memory and knowledge retrieval before each fix dispatch adds tool calls to the loop; in pathological cases (many unique failures), this overhead is additive. The per-query cache on the knowledge layer (ADR-0008) bounds the cost for repeated queries within a task.

### Neutral
- The maximum iteration count and pass-rate/coverage thresholds are configurable per task and per tenant, allowing operators to tune aggressiveness of the automated fix loop.
- The Tester role may call `claude_code.*` tools (ADR-0012) to generate spec files; this is the one permitted use of deep-coding worker dispatch from the Tester role, scoped to spec generation only — not to fixing application code, which remains the Coder's responsibility.
